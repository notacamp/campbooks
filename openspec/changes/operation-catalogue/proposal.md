# Proposal

## Why

ADR 0008 asks every module to declare its operations once, so the API, the
client, the command menu, the assistant's tools, automation and MCP agree.
ADR 0013 settles how: the OpenAPI document generated from the handlers is
that single catalogue, with a stable `operationId` and one `x-campbooks`
extension per operation. A separate action registry (generic action
endpoints, undo tokens, backend shortcuts) was tried first and rejected as a
second description to keep in sync.

Before the first real module lands, the kernel needs the pieces every module
will use: the declaration itself and its checks, an events catalogue for
rules and projections, a way for automation and the assistant to run an
operation by id with the same checks as HTTP, idempotency for every write,
and a cross-module record reference.

Tracking issue: https://github.com/notacamp/campbooks-cloud/issues/50.

## What Changes

- **Operation identity and metadata.** Every operation's `#[utoipa::path]`
  carries `operation_id = "<module>.<verb>[_<noun>]"` and
  `extensions(("x-campbooks" = json!(Operation::…)))` with `mutates`, `undo`,
  `automation`, `assistant`, `risk` (`low|high`) and `records`.
  `kernel::Operation` builds it. **BREAKING** for API clients: `system_health`
  and `system_version` are now `system.health` and `system.version`.
- **Checks.** `cargo xtask arch` fails unless every operation has an
  `operationId` prefixed by the module whose router serves it, unique ids, a
  complete and well-typed `x-campbooks`, `mutates` matching the method,
  records of its own module, and `undo` naming an existing mutating
  operation. Security is still checked as before.
- **Events catalogue.** Modules declare published events with
  `Background::publishes::<E>()` (`E: DomainEvent + ToSchema`).
  `DomainEvent` gains `WORKSPACE_SCOPED` (default `true`). The registry
  rejects misnamed, unversioned or duplicate declarations;
  `openapi/events.json` is generated by `cargo xtask events` and printed by
  `campbooks-server events catalogue`; CI checks it is current; `cargo xtask
  arch` fails when a consumer reads an event no module publishes, or at
  another version.
- **Invoke by id.** `kernel::operations::invoke(&state, Invocation)` runs an
  operation through the same router HTTP requests reach, for a principal,
  after checking that the operation opts the caller kind (automation or
  assistant) in, that high-risk calls are confirmed and that mutating calls
  carry an idempotency key. `kernel::operations::compose` builds that
  router for the server.
- **Idempotency.** One middleware in front of every module route honours
  `Idempotency-Key` for mutating operations, stored in the new
  `kernel.idempotency` table and pruned hourly by `kernel.prune_idempotency`.
- **`RecordRef { type, id }`** in the kernel.

## Capabilities

### New Capabilities

- `operation-catalogue`: declaring operations and events, the checks over
  them, invoking operations by id, idempotent writes and record references.

### Modified Capabilities

None. `system` keeps its behaviour; only its operation ids change.

## Impact

- Crates: `campbooks-kernel` (new `operations`, `idempotency`, `records`;
  `Scoped` accepts an in-process principal; `AppState.operations`;
  `Background::publishes`; `DomainEvent::WORKSPACE_SCOPED`;
  `ConsumerInfo.event_version`), `campbooks-server` (`compose`,
  `events_catalogue`, `events catalogue` command), `campbooks-system` (ids and
  metadata), `xtask` (`check_operations`, `check_events`, `events`).
- No new module and no cross-module dependency.
- Data: table `kernel.idempotency`, owned by the kernel.
- Dependencies: no new crate. The kernel now uses `aws-lc-rs` (SHA-256;
  already the TLS and JWT backend) and `tower` as normal dependencies.
- Clients: regenerated `schema.gen.ts` (operation ids).
- Self-hosters: one migration runs on startup; nothing to configure.

## Non-goals

- A separate action registry, generic `/actions/{name}` endpoints, undo
  tokens or backend-declared shortcuts (rejected by ADR 0013).
- The automation module, the assistant's tool generation and the MCP server;
  they consume this catalogue later.
- User-defined custom actions (webhooks, Slack, Notion); they are data owned
  by the automation module.
- Real domain operations or events; none exist yet besides `system`'s probes.
- Atomicity between a handler's transaction and the stored idempotent
  response (a crash in between lets a retry run again).
