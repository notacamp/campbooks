# Design

The decision and its alternatives are in ADR 0020. This file covers how it
is built.

## Data ownership

- `kernel.tracked_events`: the outbox. Columns: `id uuid` (UUIDv7, the
  event id), `workspace_id uuid` (nullable for instance-wide events), `name`,
  `version`, `occurred_at`, `envelope jsonb` (actor, on behalf of,
  operation, correlation, causation, role, app and plan version), `body
  jsonb` (properties and record snapshots), `published_at` (null until the
  relay confirms it, #321). Row-level security matches `kernel.events`: a
  workspace transaction appends only its own workspace's rows, and the
  runtime role can't read or change them back (the relay reads through a
  definer function in #321): one `workspace_isolation` policy (the kernel
  scope, or the transaction's own workspace) and `INSERT` only for the
  runtime role. An instance-wide event is written from a transaction that set
  no workspace, which the kernel lifts into the kernel scope for that insert,
  as it does for instance-wide domain events; a workspace transaction may not
  add one. Migration `<ts>_kernel__tracked_events.sql`.
- `kernel.jobs.origin jsonb` (nullable, ≤ 1 KB, ids and enums only): the
  ambient actor, on behalf of and correlation when the job was enqueued or the
  delivery fanned out: `{actor?: {type, id?}, correlation}`, the actor being
  the context's `on_behalf_of`, else its actor unless that is `system`. A
  larger origin is dropped rather than refusing the enqueue. Migrations
  `<ts>_kernel__job_origin.sql` (the column and a `NOT VALID` check) and
  `<ts>_kernel__job_origin_validate.sql`. The payload audit
  (`xtask/src/payloads.rs`, `JOB_ORIGIN_FIELDS`) lists the fields of
  `JobOrigin` and `Actor`.

## The tooling: a standalone crate

The workbook tooling is the crate `crates/tracking-plan` (package
`campbooks-tracking-plan`, a library and a binary). It depends on no other
Campbooks crate, so CI and agents run it without building the server
(`cargo run -p campbooks-tracking-plan -- <cmd>`); `cargo xtask tracking
[--check | generate | fmt | apply <patch> | init]` is a thin wrapper over the
library. `cargo xtask arch` knows it as a tooling crate: it depends on no
workspace crate, and only xtask may depend on it. Dependencies: `calamine`
(read), `rust_xlsxwriter` (write) and `serde-saphyr` (YAML patches, a
pure-Rust parser; `serde_yaml` is unmaintained), in this crate only.

Commands: `init` (a new workbook), `check` (CI), `generate` (the mirror and
every `tracking.gen.rs`, removing stale ones), `fmt` (canonical workbook) and
`apply <patch.yaml>` (add or replace rows by key, remove rows by key, then
`fmt` and `generate`; nothing is written when the patched plan breaks a
rule). Patches live in `tracking/patches/` as the history of agent edits;
people may edit the workbook directly.

Determinism: generated `.rs` and `.json` are byte-stable (sorted keys and
rows, a trailing newline, a `// @generated by campbooks-tracking-plan — do
not edit` header, rustfmt-clean by construction). The workbook `fmt` and
`apply` write is byte-stable too: rows sorted, fixed styles, and the
document's creation date set to the plan version's date. `check` compares
parsed content, never workbook bytes, so a workbook saved by Excel or
LibreOffice passes.

The workbook is a tracking plan a person opens in Excel: a styled, frozen
header row, column widths, dropdowns on closed-set columns (scope, status,
type, list, required, classification, coverage kind) with an input hint on
every column, an autofilter on each table, and a README sheet (rewritten on
every write) with the naming rule, the classification table, how to add an
event and how to run the tool.

## The plan workbook

| Sheet | One row per | Key columns |
| --- | --- | --- |
| README | — | how to edit, naming rules, the classification table, plan version |
| Events | event version | name, version, module, object, action, scope (`workspace`/`instance`), status (`planned`/`live`/`deprecated`), actor types, description, fires when, added in (plan version), OpenSpec change |
| Properties | event property | event, version, property, type, list, enum or record, required, classification, pattern, description, example |
| Records | snapshot field | record type (`<module>.<record>`), field, type, list, enum, required, classification, pattern, description |
| Enums | enum value | enum, value, description |
| Actors | actor type | type, id is, description (fixed rows: user, client, assistant, automation, system, admin, anonymous) |
| Coverage | operation / job / schedule / handler | kind, name, events (comma-separated), exemption reason |
| Changelog | plan change | date, plan version, change, PR |

Property types: `id`, `record_ref`, `record` (a snapshot from Records),
`enum`, `bool`, `int`, `decimal`, `duration_ms`, `timestamp`, `date`,
`bytes`, `currency`, `country`, `locale`, `code` (needs a `^…$` pattern).
Any type except `record` may be a list: a `List` yes/no column (in the mirror
the schema is an array), because a dropdown of every `list<type>` would pass
Excel's 255-character limit on list validations. The plan version is the
newest Changelog row's. Classifications: `id`,
`pseudonymous`, `operational`. `personal` and `content` are valid for
writing down what a field *would* be, and the check rejects them, so a
rejected field shows up in review instead of being dropped without notice.

## Checks (`cargo run -p campbooks-tracking-plan -- check`, in CI's Rust job)

1. The workbook parses; sheets and headers are as above (no other sheet or
   column); dropdown values are in their sets.
2. Names follow `<module>.<object>_<past_verb>`, the module exists, and
   `(name, version)` is unique. Only the newest version of an event may be
   `live` alongside `deprecated` older ones.
3. Every property and record field has an allowed type and classification;
   `code` has a pattern; enums and records referenced exist; nothing is
   `personal` or `content`.
4. The mirror and every generated file equal what the workbook produces.
5. Every `live` event's generated type is used outside `*.gen.rs` and tests
   in its owning crate (a text scan, like `xtask/src/payloads.rs`); a
   `planned` one isn't (it must become `live`). Nothing outside generated
   code and tests implements `TrackedEvent`. Each generated file is included
   by its crate.
6. Coverage: each row lists events that exist, or an exemption, not both.
   Rows of kind `operation` name an `operationId` of `openapi/openapi.json`
   or `openapi/admin.json` (read as JSON files). Mutating operations with no
   row are reported as warnings.
7. Jobs, schedules and handlers are checked by a server test
   (`crates/server/src/tracking_tests.rs`) that builds the real registry and
   catalogue: a row naming an unknown kind fails; mutating operations and
   kinds with no row are printed as warnings. #332 turns them into failures
   (`REQUIRE_FULL_COVERAGE`).

## Generated code

One `tracking.gen.rs` per owning crate (`crates/modules/<m>/src/` or, for
kernel- and server-owned events, `crates/kernel/src/tracking/`), included by
a hand-written `#[path = "tracking.gen.rs"] pub mod tracking;`. The kernel's
always exists and holds `PLAN_VERSION` and `PLAN_DATE`. Per event: a struct with typed fields (snapshots as
generated `<Record>Snapshot` structs, enums as generated enums) and an
`impl TrackedEvent` carrying `NAME`, `VERSION`, `MODULE` and whether it is
workspace-scoped. A workspace-scoped event has a `workspace` field, written
into the envelope, not the body. Modules fill snapshots from their own rows.
The generated structs can only be built with every required field; types
come from `campbooks_kernel::tracking::types`, so a module needs nothing
beyond the kernel and `serde`.

## The ambient context

`TrackingContext` is a tokio task-local:

- **HTTP**: a layer (`kernel::tracking::http`) opens the context with
  `operation` from the matched route's `operationId` and `correlation` from
  the request's trace id (a fresh id when nothing is traced), as `anonymous`.
  The `Scoped` extractor (and so `Workspace`) then names the principal: `user`
  with the Campbooks account id (the token's subject, ADR 0014), `client`
  with the client id. On admin routes the `Admin` extractor names `admin`
  with the account id of the grant. Routes nobody authenticates on (sign-up,
  sign-in) stay `anonymous`. The layer lives in the kernel, because
  `operations::compose` (which both HTTP requests and `invoke` go through)
  and `testing::app` apply it; the server applies it to its admin, BFF and
  issuer routes.
- **Assistant and automation** wrap the operations they invoke on someone's
  behalf: actor `assistant` / `automation`, `on_behalf_of` the person.
- **Jobs**: the worker sets actor `system` (id = job kind), `on_behalf_of`
  from `origin.actor` when present, `correlation` from `origin`, and
  `causation` = the job id, or for a delivery, the event id.
- **Outside any context** (CLI, startup), `track` uses `system` with the
  command's name. It never fails because the context is missing.

`Tracker::track(&mut tx, &E)` checks that the transaction's workspace
matches the event's (as `EventBus::publish` does), builds the envelope from
the context, and inserts the row. With `SINK=none` it returns at once
without touching the database.

## Reference flow

`conversations.archive` (and its undo, `conversations.unarchive`) track
`conversations.conversation_archived` / `conversations.conversation_unarchived`
v1 with a `conversations.conversation` snapshot: `id`, `inbox_id`, `stream`,
`stream_source`, `status` (`inbox`, `archived`, `trash`, `spam`),
`message_count`, `unread_count`, `starred` and `last_message_at` (its last
activity), read from the module's own rows after the change, in the
handler's transaction, and only when the change changed something. The
conversation has no attachment flag of its own, so the snapshot has none.
The Coverage sheet maps both operations.

## Events published or consumed

None. This change adds tracked events, not domain events.
