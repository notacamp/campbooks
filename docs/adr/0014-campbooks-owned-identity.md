# 0014 — Campbooks owns identity: every owned mailbox is a way in, and Campbooks issues the tokens

**Status:** Accepted · 2026-10-13 · supersedes [0004](0004-oauth-dedicated-idp-bff.md)

## Context
ADR 0004 put sign-in and token issuance in a dedicated identity provider,
Rauthy. The product has since settled what sign-in must do, and Rauthy
cannot do it:

1. **The provider account you first sign in with is also your first
   mailbox**, granted in one consent (identity scopes, mail scopes and
   offline access together).
2. **Every mailbox you own is a way in** to the same account, interchangeably.
   Connecting another Google, Microsoft or Zoho mailbox while signed in adds
   it as a sign-in method. Passkeys are a way in too.
3. **Linking is by proven ownership** (an OAuth round trip completed while
   signed in, or the one that created the account), never by matching email
   addresses: Microsoft does not verify the `email` claim, so matching by
   email is an account-takeover path.

Rauthy 0.37.1 (read in its source) links an account to **one** upstream
provider, never hands the upstream tokens to the application (so the mailbox
grant cannot come out of a sign-in), and has no admin API to set a
federation id. Working around all three would mean a fork. Its login screens
also lack pt-PT and es-ES, which AGENTS.md makes a blocker for any screen we
put in front of users.

The bar ADR 0004 set for the token side is unchanged and is the bar here:
authorization code with PKCE (S256 only) and single-use codes;
client_credentials; refresh-token rotation; JWT access tokens with a JWKS
and key rotation; our own scopes; audience binding (RFC 8707); API-driven
client registration, per workspace; per-client claims such as
`workspace_id`; passkeys; zero-manual-step upgrades for self-hosters.

## Decision
- **A new module, `identity`** (`crates/modules/identity`, schema
  `identity`), owns accounts, their credentials (provider identities and
  passkeys), browser sign-in sessions, and the authorization server's state:
  clients, authorization codes, refresh-token families, consents and signing
  keys.
- **Campbooks is the OAuth 2.1 authorization server and OpenID provider**,
  in-process, on the app's own origin. The issuer is `CAMPBOOKS_PUBLIC_URL`;
  discovery at `/.well-known/openid-configuration` and
  `/.well-known/oauth-authorization-server`, protected-resource metadata at
  `/.well-known/oauth-protected-resource` (RFC 9728, for MCP), protocol
  endpoints under `/oauth2/*`. It is **hand-rolled on crates already in the
  graph** (`jsonwebtoken`, `aws-lc-rs`) with a narrow profile (code + PKCE
  S256, client_credentials, refresh_token; nothing else) and RFC conformance
  tests, plus an OpenID conformance-suite run on staging before #57.
- **The API stays a standard resource server.** The kernel's verifier is
  unchanged except where it gets keys: from the in-process key set instead of
  an HTTP fetch. Third parties can still fetch `/oauth2/jwks`.
- **Upstream providers (Google, Microsoft, Zoho) are relying-party flows
  owned by `identity`**: one front door for every provider consent, whether
  it signs someone in, adds a way in, connects a mailbox or reconnects one.
  The mailbox grant is handed to `connectors` through a kernel port
  (`GrantIntake`) that `connectors` implements over its
  `create_or_refresh_connection` seam. A grant obtained before any
  workspace exists is held, sealed, by `identity` until the person creates
  or chooses their first workspace (at most 7 days).
- **The web BFF is an OIDC client of the in-process issuer**, as it was of
  Rauthy: the browser still holds only the session cookie. Its client is
  first-party (no consent screen) and needs no provisioned secret.
- **Signing keys are Ed25519**, generated by the server, sealed at rest
  with a key derived from `CAMPBOOKS_SECRET_KEY`, rotated every 30 days and
  published 7 days before use.
- **Login, provider choice, new-account, passkey and consent screens are
  Campbooks screens** in `clients/`, in en, pt-PT, es-ES and fr.
- **Rauthy is removed**: the `idp`, `idp-init` and `idp-provision` services,
  `deploy/idp/`, its settings and its docs.

The design and its alternatives are in the first slice's change,
`openspec/changes/archive/2026-10-13-campbooks-identity-s1a/design.md`.

## Slices
Each is one pull request with its own OpenSpec change and recording,
tracked as a sub-issue of campbooks-cloud#75:

1. **S1a** (#77): the issuer, its keys, Google sign-in, the held mailbox
   grant and its hand-off, the BFF on the in-process issuer.
2. **S1b** (#78): the sign-in and new-account screens, and first-run's
   "connect this mailbox here".
3. **S2** (#79): more ways in (link, connect, reconnect, remove), Microsoft
   and Zoho, and `connectors`' consent through `identity`.
4. **S3** (#80): passkeys.
5. **S4** (#81): native apps, workspace clients, consent, DCR and client
   metadata documents for MCP agents.
6. **S5** (#82): Rauthy removed and staging cut over.

After S1a, S2–S5 can proceed in parallel. The OpenID conformance suite runs
against staging, then security review #57, before production.

## Consequences
- We own security-critical code: token issuance, refresh-reuse detection,
  WebAuthn verification, upstream ID-token validation. That is the cost ADR
  0004 avoided. It is paid down by a narrow profile, conformance tests
  against the RFCs, the OpenID conformance suite on staging, and the
  security review (#57) before production.
- Self-hosters run three fewer services and back up one thing fewer (the
  `idp-data` volume). Everything identity needs is in Postgres;
  `CAMPBOOKS_SECRET_KEY` (already generated by `server-init`) protects the
  signing keys and held grants. A server whose secret key cannot open the
  signing keys refuses to start rather than replace them; starting over
  (deleting the keys) signs everyone out and drops held grants, while
  passkeys and links survive.
- One Google, Microsoft or Zoho OAuth app per provider serves sign-in and
  mail, registered with one redirect URI on the app origin:
  `<app-origin>/auth/callback/<provider>`.
- Signing up with Google asks for a restricted Gmail scope in the same
  consent. Until the app passes Google's verification (#53), new users see
  Google's "unverified app" screen at sign-up, not only when connecting mail.
  The owner accepted this: one consent, no fallback switch.
- There is no Campbooks password. People sign in with a provider or a
  passkey; providers keep their own MFA, passkeys are phishing-resistant.
- `workspaces.users.idp_subject` now holds a Campbooks account id; the
  `workspaces` module needs no schema change.
- The `connectors` module's own Google consent flow (#450) becomes a
  delegate of `identity`'s front door; `connectors` keeps refresh, revoke and
  health.

## Alternatives considered
- **Keep Rauthy and work around it** (Campbooks links several Rauthy
  subjects; a second consent for mail). Fails requirements 1 and 2: two
  consents, the upstream tokens never reach us, and linking needs a Rauthy
  fork.
- **Ory Hydra as the token issuer with our own login/consent app.** Hydra
  delegates login and consent to us, so the identity rules above would still
  be ours, and Hydra brings OpenID-certified issuance, DCR and key rotation.
  Costs one more service (Go), its own schema and a `hydra migrate` init step
  on every upgrade, and an admin API between two processes for every client
  registration. Kept as the fallback if our issuer fails conformance or
  review.
- **An AS crate (`oxide-auth` 0.6.1).** Last release June 2024, no OpenID
  Connect, no DCR, no refresh-reuse detection, older `rand`/`base64` lines.
  We would still write most of the profile.
- **Sign-in inside the BFF only** (the BFF talks to the providers and mints
  sessions; no authorization server). Smallest for the web, but native apps,
  third-party clients and MCP agents still need an issuer, so it would be a
  second path to maintain.
